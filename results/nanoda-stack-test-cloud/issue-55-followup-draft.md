# DRAFT (not posted) follow-up comment for https://github.com/ammkrn/nanoda_lib/issues/55

Some more detail on SquareDifference with f67473b, in case it helps. Its stack overflow comes from five declarations; four of them have one cause that I think I've pinned down, the fifth is different and I haven't.

**Four of them (`tupleSubLaw_full`, `tupleLaw_decomposition`, `tupleGoodLaw_probability`, `tupleEta_le`): alpha-equivalent terms with different binder names.** The recursion compares `DFunLike.coe m φ₁` with `DFunLike.coe m φ₂`, where `m` is the same pointer and φ₁, φ₂ are both `fun x => (1 : ℝ)`, differing only in the binder name (`x._@.OAI.Combinatorics.SquareDifference.MarkedTuples…_hyg.46` vs `x._@…CrossProducts…_hyg.56`). Since the binder name is part of an expression's hash and identity (in `parser.rs` and in `mk_lambda` / `mk_pi`), the two are different pointers, `def_eq_quick_check` misses them, and `def_eq` unfolds `m` (a long sum of additive maps) instead, which in practice doesn't finish. As a check, the attached patch adds a structural equality test that ignores binder names and styles (memoised over pointer pairs) at the start of `def_eq`; with it all four check in 1.5 to 4.4 s, and the other configurations I re-ran (DirectedFeedback, MinUncut, BinPackingGap, KMedianThreshold, ContinuumCoulombHardness, Catalan) pass at the same or slightly better times. It's meant only to confirm the diagnosis; you'll know better where such a check belongs, or whether identity should simply ignore binder names.

**The fifth, `OAI.SquareDifference.source_ordered_contraction`, is something else.** With the patch it still overflows, this time with `whnf` and `whnf_no_unfolding_aux` nesting through `List.rec` reductions along a long list. Lean's kernel accepts it, but it is heavy there too (74 s of replay). I haven't found out why nanoda nests here; I can provide the export (495 MB) if useful.
